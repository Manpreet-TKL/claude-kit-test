# NOD Audit module validation vs legacy NOD Export

Scope: NodAudit special module (new) validated on a test deployment against the saved
legacy export `RMC_202607241624_NOD_Export.zip` (Cataract only, 01 Apr 2025 - 31 Mar 2026).

Provenance of the baseline: the zip was generated by `NodExportv26Command.php`, a
console hotfix created to work around the web exporter
(`protected/controllers/NodExportController.php`) timing out. The command is a
near line-for-line console port of the controller - the zip's filename pattern
(`<institutionCode>_<YmdHi>_NOD_Export.zip`) matches the command's naming. Line
references `Cmd:` = NodExportv26Command.php. Except where section 7 says otherwise,
every defect listed is inherited verbatim from the controller, so the findings
apply to the old approach as a whole, not just to the hotfix.

Verdict up front:

1. The new module works end to end once a worker runs; the full Cataract run
   completes in **17 seconds** (requirement: under 5 minutes) after a two-part fix
   to the IMD postcode lookup.
2. Every row-count difference between old and new output traces to a defect in the
   legacy exporter, not to a fault in the new module. The new output is internally
   consistent (zero orphan keys across all 19 CSVs), is a strict, correctly
   filtered subset of the legacy cohort, and is byte-reproducible across runs.
3. No DDL outside the module's own setup migrations. Runtime writes are confined to
   session-scoped `CREATE TEMPORARY TABLE` on a dedicated reader connection and the
   module's own `nod_audit_run` / `nod_audit_setting` tables.

---

## 1. Why it "just sat waiting for queue"

The web UI never extracts anything: it only queues a run into `nod_audit_run` and
monitors it. Extraction is done by a worker command, `yiic nodauditworker`, which is
expected to run every minute from cron on the master/manager container. This test
deployment has no container with the module and a cron entry, so queued runs waited
forever. This matches the module README's troubleshooting entry ("Run stays queued
forever: worker cron not running").

Manual trigger (any container with the module and DB access):

`docker exec <web-container> php /var/www/openeyes/protected/yiic.php nodauditworker`

The worker takes a named DB lock, marks orphaned `running` runs as failed, claims the
oldest `queued` run, streams all stage CSVs, zips them, and sets the run `complete`
so the UI offers the download. For production the missing piece is only the cron
entry on the master container.

## 2. Performance: requirement "whole run under 5 minutes"

### 2.1 The blocker

First full run stalled in stage `Cataract/Patient`: 500+ seconds without completing
1,013 patients. `EXPLAIN` showed the postcode-to-LSOA lookup doing a full scan of
`postcode_to_lsoa_mapping` (2.6M rows, `possible_keys NULL`) with a filesort **per
patient**, inside this correlated subquery:

```sql
WHERE ptlm.postcode IN (a.postcode, REPLACE(a.postcode, ' ', ''))
ORDER BY (ptlm.postcode = a.postcode) DESC, ptlm.id LIMIT 1
```

Two independent causes, both required fixing:

1. **Charset coercion.** `address.postcode` is utf8mb3_bin; `postcode_to_lsoa_mapping`
   is latin1_swedish_ci. MariaDB coerces the indexed (latin1) column up to utf8,
   which disables its unique index.
2. **Correlated IN-list.** `col IN (expr1, expr2)` with non-constant expressions can
   never use an index: ref access needs a single equality, and range access needs
   constants at optimise time. Even with matching charsets this form full-scans.

This is very likely why the hotfix command deleted IMD altogether (see section 7,
item 6): the same lookup exists in the controller, and at 2.6M rows per patient it
would have appeared to hang. The rewrite fixes the lookup instead of removing the
feature.

### 2.2 The fix

Rewrite the lookup as two single-equality probes, exact postcode first, then
space-stripped (the same preference the old `ORDER BY` expressed), with the outer
reference converted so the comparison stays in the mapping table's native charset:

```sql
WHERE ltim2.lsoa = COALESCE(
    (SELECT ptlm.lsoa FROM postcode_to_lsoa_mapping ptlm
     WHERE ptlm.postcode = CONVERT(a.postcode USING latin1) LIMIT 1),
    (SELECT ptlm2.lsoa FROM postcode_to_lsoa_mapping ptlm2
     WHERE ptlm2.postcode = CONVERT(REPLACE(a.postcode, ' ', '') USING latin1) LIMIT 1))
```

Applied in `components/datasets/CataractDataset.php` (exportPatient) and
`components/datasets/AmdDataset.php` (exportPatientDetails - identical pattern).
Postcodes are pure ASCII so the conversion is lossless in this direction, and
`postcode_to_lsoa_mapping.postcode` carries a UNIQUE key, so at most one row matches
each form and COALESCE order reproduces the original exact-match preference exactly.

### 2.3 Proof

| Check | Before | After |
|---|---|---|
| EXPLAIN, `ptlm` access | ALL, 2,631,977 rows, possible_keys NULL, filesort | eq_ref on `postcode_to_lsoa_mapping_postcode_idx`, 1 row |
| Patient stage (1,013 patients) | killed after 500+ s | < 1 s |
| Full Cataract run | never completed | **17 s** total, slowest stage 6 s (PatientCVIStatus) |
| IMD populated | n/a | 993 of 1,013 patients |

No-skew evidence:

- Full-cohort equivalence: for all 1,013 patients the original IN-form and the
  rewritten form were both evaluated in one query with a NULL-safe compare of the
  selected `lsoa_to_imd_mapping` row id: **1,013 of 1,013 identical, 0 mismatches**.
  The proof run took 45.5 minutes because it had to execute the original form; the
  rewritten form covers the same cohort in under a second.
- The only semantic edge would be case sensitivity: the mixed-charset original
  compares case-sensitively (bin), the latin1 comparison is case-insensitive. On
  this database both `address.postcode` and the mapping table contain zero
  non-uppercase postcodes, so no row can differ.

Per-stage timings of the passing run (worker log): Episode 1s (48,651 rows),
Patient <1s, PatientCVIStatus 6s, DiabeticDiagnosis 1s, PreOpAssessment <1s,
Refraction <1s, Drug 4s (14,864 rows), Biometry 1s, IOP <1s, VisualAcuity 2s
(19,993 rows), all remaining operation stages <1s each.

A sweep of all module SQL found no other correlated IN-lists or cross-charset
comparisons; the only other IN-lists are PHP-interpolated constant id lists, which
the range optimiser handles.

Determinism: a second full run (10 s) produced byte-identical CSVs across all 19
files (`diff -rq` clean) - pseudonyms and fuzzed DOBs are stable across runs, so
longitudinal linkage between yearly submissions works. The legacy RAND()-based DOB
fuzz changed every run.

## 3. DDL audit

Requirement: no DDL outside the migrations that set up the module's own tables.

- Migrations (legitimate): `m260301_000000_create_nod_audit_tables.php`,
  `m260715_000000_nod_audit_queue.php` - create `nod_audit_run` / `nod_audit_setting`.
- Runtime: only `CREATE TEMPORARY TABLE tmp_nod_*` / `DROP TEMPORARY TABLE`,
  session-scoped on the dedicated reader connection; they vanish when the
  connection closes and never touch shared schema.
- Writes: only the module's own two tables (run state, per-institution HMAC key).
  Nothing else is INSERTed/UPDATEd/ALTERed. The legacy exporter, by contrast,
  creates real persistent `tmp_rco_nod_*` tables in the shared schema on every run,
  and the hotfix command additionally replaces a shared database view and leaves
  an undropped shared table behind (section 7, items 1-2).

## 4. Comparison methodology

The new export pseudonymises ids with HMAC-SHA256 (per-institution persistent key,
id spaces `P:`/`S:`/`E:`/`T:`, truncated to 31-bit ints). The legacy export used raw
database ids. Using the run's stored key, every legacy raw id was mapped through the
same HMAC and matched against the new output, giving exact row-level joins between
the two exports without de-pseudonymising anything.

Legacy zip: 21 CSVs (19 data + 2 static lookup files). New zip: the same 19 data
CSVs (lookup tables intentionally dropped; codes are now resolved to names inline).

Code analysis was performed against `NodExportv26Command.php` - the file that
actually produced the baseline - and cross-checked against the controller it was
ported from; every mechanism claimed below was verified both in the code and in the
exported data.

### Deliberate schema differences (improvements, not regressions)

1. Ids to names: Drug, DrugRoute, SurgeonGrade, RefractionType, IOP Instrument -
   removes the need for the dropped lookup CSVs and for NOD-side decoding.
2. Biometry: device-id columns dropped, adds Formula, TargetRefraction,
   SelectedIOLPower, PredictedRefraction, SelectedLens (the outcome-relevant data).
3. VisualAcuity wide-to-long (Method, LogMAR): one row per measurement method
   instead of unit-dependent duplicated wide rows.
4. Operation: adds the actual operation Date; drops free-text Description,
   IsHypertensive (belongs to co-pathology) and the misleading ListedDate.
5. PostOpComplication: adds Date, and OperationId now genuinely references the op.
6. TreatmentCataract: adds PCRRiskScore and PhacoCDE; keyed one row per op+eye.
7. Treatment: adds SnomedCode/SnomedTerm.
8. Surgeon: adds Surname and CurrentGradeDescription.
9. Episode: Seq (hardcoded 1 in old, Cmd:1442, emitted Cmd:1535) replaced by
   EventType.

### Pseudonymisation differences

| Aspect | Old | New |
|---|---|---|
| Patient/op/surgeon ids | Raw database ids (re-identifiable against source) | HMAC-SHA256 per-institution key, 31-bit ids, stable across runs |
| Date of birth | Random +1-3 months per run via RAND() (Cmd:1266), real day-of-month kept (961/1,013 rows leak the true day) | Deterministic per-patient 1-3 month shift, day pinned to 01 |
| Reproducibility | Different DOBs every run, so yearly submissions cannot be linked | Byte-stable across runs (see determinism check) |

## 6. What was definitely wrong in the old way

All present in the baseline generator; all but the section 7 items are inherited
verbatim from the web controller.

Functional:

1. Cohort includes any op-note type; no cataract-element check (Cmd:1450) -
   751 non-cataract patients in a Cataract audit.
2. Detail extracts have no date bound at all (Cmd:1465-1527) - lifetime history
   exported (Episode rows back to 1991, ops listed 2017).
3. Right-eye biometry rows carry left-eye values (Cmd:1992-2013) - every legacy
   right-eye biometry measurement is wrong (1,334/1,334 in this export).
4. PostOpComplication.OperationId is the exam event id (Cmd:2291) - 0/2,354 rows
   attributable to an operation.
5. Anaesthesia INNER JOIN on complication tables (Cmd:2908-2909) drops most
   operations' anaesthesia records (627 rows vs 1,637 real).
6. OperationIndication eye filter dead in a LEFT JOIN ON clause
   (Cmd:3113-3116/Cmd:3139-3142): every op doubled L+R, missing indications
   fabricated as id 0 (Cmd:3096).
7. PreOpAssessment risk flags query the op-note event for examination-only
   elements (Cmd:1586-1613/Cmd:1634-1661): constants stamped on every patient
   (verified across all 3,252 rows); right-eye GROUP BY omits 2 columns
   (Cmd:1669).
8. PatientCVIStatus empty: the examination query is overwritten by the legacy
   CVI-event query (Cmd:1348-1367) on deployments recording CVI in examinations.
9. DiabeticDiagnosis joins all diagnoses to all events, no DISTINCT
   (Cmd:1176-1188): 60% duplicate rows, non-diabetes rows emitted as IsDiabetic=0.
10. Drug rows cross-multiplied events x all prescriptions ever (Cmd:1864-1870);
    Eye derived from route ids (Cmd:1840).
11. DOB fuzz random per run and leaks true day-of-month (Cmd:1266); ids are raw
    database keys.
12. Hardcoded/placeholder outputs: Episode.Seq=1 (Cmd:1442), IOP Type='' and
    GlaucomaMedicationStatusId=9 (Cmd:2110/Cmd:2128), RefractionTypeId/ReadingAdd=''
    (Cmd:1736-1770), IncisionPlanesId=4 (Cmd:2733), ListedDate=event date
    (Cmd:1440/Cmd:3346), VA NotationRecordedId = raw unmapped unit id (Cmd:3430).

Performance:

1. Chunked LIMIT/OFFSET paging with re-executed source queries (Cmd:393-428, loop
   at Cmd:397/Cmd:404): O(n^2) paging cost on big extracts, and without a stable
   ORDER BY the chunk boundaries can drop or duplicate rows (the hotfix made this
   worse - section 7, item 4).
2. Cartesian fan-outs do the explosion work before filtering: 1.76M drug rows and
   800k diagnosis rows generated for what should be ~15k rows.
3. Real persistent `tmp_rco_nod_*` tables created in the shared schema each run
   and left behind on failure; the new module uses session temporary tables that
   cannot leak.
4. Provenance context: the web controller ran the entire export synchronously
   inside the POST request and read the whole zip into memory to serve it - the
   timeouts this caused are why the hotfix command exists. The new module
   queues the run and a worker streams it, with progress, cancel and download.

## 7. Defects specific to the hotfix command

Introduced by the port itself; not present in the web controller.

1. **Replaces a shared database view.** During an AMD export the command
   `CREATE OR REPLACE VIEW`s `v_patient_events` (Cmd:215-326; the view DDL at
   Cmd:273-315). This swaps a live, shared production view mid-export: any
   concurrent application reader sees the export's definition. The two date
   predicates are also inconsistent (`>` at Cmd:268 vs `>=` at Cmd:323).
2. **Undropped shared table.** The DROP for `tmp_evii` is assigned to a
   misspelled variable, `$qqlquery` (Cmd:376), and never executed - the table
   persists after every run. These working tables are also unsuffixed shared
   names (Cmd:318-321), so two concurrent runs clobber each other.
3. **Right-eye refractions dropped.** Both stable-refraction CTE branches filter
   `sr.eye_id = 1` (Cmd:1732 and Cmd:1762 - the right-eye branch was never
   updated), and the INNER JOIN at Cmd:1776 then discards any refraction event
   that only has a right-eye reading. Verified in the data: old L 7,708 vs
   R 7,434 where symmetry is expected (new: 3,607/3,601). The GROUP BY at
   Cmd:1749/Cmd:1779 is also indeterminate, so which reading wins is arbitrary.
4. **Removed ORDER BYs on the three biggest files.** The controller ordered the
   Episode, Drug and DiabeticDiagnosis outputs; the command dropped those ORDER
   BYs (Cmd:1534-1538, Cmd:1879-1882, Cmd:1195-1199). Combined with the
   LIMIT/OFFSET paging (Cmd:393-428) the chunk boundaries are non-deterministic:
   rows can repeat or vanish between chunks exactly on the files most likely to
   page.
5. **INSERT IGNORE.** Cmd:3199 swaps the controller's plain INSERT for INSERT
   IGNORE, silently discarding duplicate-key rows instead of surfacing the
   underlying fan-out bug.
6. **IMD deleted.** The postcode/LSOA/IMD lookup chain is removed and literal
   NULLs selected in its place (Cmd:1268-1271, orphaned `address` join Cmd:1275;
   AMD the same, Cmd:814-817) - which is why 0/1,764 baseline patients carry IMD.
7. **Fragile argument handling.** `run()` requires exactly 4 positional args
   (Cmd:81) and an unrecognised audit name silently falls through to AMD
   (Cmd:102-105) - a typo in "Cataract" runs the wrong audit.
8. **Lost tie-breakers.** Deterministic ORDER BY tie-breaks present in the
   controller were dropped (Cmd:2228, Cmd:2263, Cmd:2714), making which row wins
   arbitrary where duplicates exist.
9. Minor: `fputcsv` escape argument lost; indexes dropped from some working
   tables.

## 8. Follow-ups

1. Deploy: add the per-minute `nodauditworker` cron entry to the master container;
   without it every run waits forever (the observed symptom).
2. The IMD lookup fix needs committing in the module repo (two files:
   `components/datasets/CataractDataset.php`, `components/datasets/AmdDataset.php`).
3. Optional hardening: align `address.postcode` / mapping-table charsets at schema
   level to remove the need for CONVERT (not required for correctness now).
